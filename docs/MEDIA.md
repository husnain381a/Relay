# Profile photos and workspace logos

Relay now includes real private-image upload helpers and settings controls. They require the migration `20261028193249_private_profile_media.sql`, authenticated Supabase access and the private `profile-media` bucket. There are no placeholder users, automatic sample images or public avatar URLs generated by this feature.

## User flow

`ProfileImageSettings` lets a user choose, preview, save or remove their profile photo. `WorkspaceImageSettings` provides the same actions for a workspace logo; the caller should expose it only to workspace owners/admins, and database/storage authorization enforces that requirement independently.

Choose image opens the native file picker. Local validation explains an unsupported format, invalid header, oversized file or excessive dimensions near the control and focuses the error for keyboard/screen-reader access. The chosen image is decoded and re-encoded locally, previewed with a browser-created object URL, and transferred only after Save. Cancel discards the selection. Processing/saving states disable conflicting actions; selected preview URLs are revoked when replaced or unmounted. The preview's dimensions stay fixed while it loads.

The current signed-in user is verified before mutation. Profile settings also pass their expected profile ID; a session switch cannot silently apply an old settings action to the newly signed-in account. Remove clears both `avatar_path` and any legacy `avatar_url`, so the old external image does not reappear.

## Limits and image handling

- Accepted formats: JPEG, PNG and WebP; maximum input and saved file size is 2 MiB.
- UUID-only object paths: `avatars/<user>/<object>.jpg|png|webp` and `workspaces/<workspace>/<uploader>/<object>.jpg|png|webp`. User filenames never become object paths.
- The client checks file signatures against MIME and reads PNG, JPEG and WebP frame dimensions **before** allocating decoded pixels. Each source dimension must be 1–4096 pixels.
- The browser must successfully decode the local file. Canvas output is resized to a longest side of at most 512 pixels and re-encoded, dropping original file metadata and flattening animation into the decoded image. An unsupported/failed decoder produces an actionable error.
- SVG and GIF MIME types are rejected. A remote URL or supplied `blob:` URL cannot be used as an upload source or stored media path. Local preview blobs are created only from the prepared raster file.
- Bucket restrictions enforce the allowed MIME set and 2 MiB size for Storage API uploads. Browser decoding is an additional client pipeline, not a server-side content scanner; hostile direct API clients cannot be assumed to follow that pipeline. This feature does not implement malware scanning or a trusted image-processing worker.

Images render through normal `img` elements. No uploaded image is interpreted as markup, evaluated, embedded in an iframe, or opened through a privileged desktop bridge.

## Authorization and persistence

`profiles.avatar_path` and `workspaces.logo_path` store private paths, never expiring URLs. `set_avatar(p_path)` and `set_workspace_logo(p_workspace_id,p_path)` select an existing uploaded object through checked RPCs. Profile selection is self-only; workspace selection requires an owner/admin role and an object uploaded by that user for the same workspace. Ordinary clients have no direct grant to assign these new path columns.

Storage policies allow avatar writes only beneath the authenticated user's folder. Workspace-logo writes additionally require current workspace administration. An unlinked/staged upload is readable only by its uploader under the relevant membership rules. A published avatar is readable by its user and users with a shared workspace; a published logo is readable by current workspace members. Outsiders and former members cannot obtain new signed access. Workspace logo changes are audited, and identifier-only profile/workspace invalidations let connected clients refresh their records.

The save flow uploads a new immutable object with `upsert:false`, publishes the checked path, then attempts to remove a previous upload only when that old path belongs to the same uploader and target scope. Another administrator's old logo is intentionally left for an authorized retention worker rather than deleted by this client. RPC failure attempts to remove only the newly uploaded unused object. A cleanup failure is reported separately from a successful image change.

Database deletion policies require uploader ownership and an unreferenced object. Reference changes and deletion checks share a per-path advisory transaction lock, so another tab cannot delete an image that was concurrently selected as current. Storage API deletion is used; internal `storage.objects` rows are never deleted by the browser as a substitute for physical object removal. Abandoned uploads and other administrators' replaced logos still need the operational retention/orphan-cleanup process.

## Expiring signed access

`PrivateMediaImage` obtains a 60-second signed URL after Storage authorization. It accepts only the configured Supabase origin and `/storage/v1/object/sign/profile-media/` route; remote, public-bucket, attachment, credential-bearing and `blob:` URLs are rejected. HTTP is accepted only for a configured loopback development endpoint.

URLs live in component/session memory. A bounded cache deduplicates concurrent requests for the same path. Visible images renew access before expiry, become fallbacks when signing fails, and retry once after an image-load failure. Hidden tabs do not issue renewal requests; visibility/authentication changes refresh access. Auth changes clear the shared cache. The global profile's `avatar_url` is not replaced with a short-lived signature.

Already issued signatures may remain usable for their remaining lifetime, and an image a user already downloaded/displayed cannot be retracted. A removed member must fail subsequent signing/read checks; do not promise immediate withdrawal of an existing signed link. Do not log signed URLs or persist them in database rows, localStorage, source artifacts or telemetry.

## Component integration

```tsx
<ProfileImageSettings profile={profile} onUpdated={reloadWorkspaceData} onError={showError} />
<WorkspaceImageSettings workspace={workspace} onUpdated={reloadWorkspaceData} onError={showError} />
<PrivateMediaImage path={profile.avatar_path} alt={profile.display_name} fallback={initials} />
```

The settings components reuse the application's existing control classes and semantic color variables. The application owner wires the controls into profile/workspace settings and passes `avatar_path`/`logo_path` to image displays. Workspace role visibility in the UI is a convenience; RLS/RPC checks remain authoritative.

## Verification and remaining gates

`tests/profile-media.test.ts` has 32 passing local tests. They execute real byte/header, dimension, path, ownership-scope and signed-address validation. Isolated client contract tests additionally check publish-before-cleanup, rollback of only the new object, another uploader's logo retention, stale-account rejection and honest cleanup-failure reporting. Those client doubles are **not** a live Supabase Storage test. Typecheck passed after implementing the components.

The database agent maintains the migration's adversarial PostgreSQL policy/RPC tests separately. PGlite can verify policy semantics but does not execute the hosted Storage service's byte/MIME enforcement or signed HTTP delivery. Live backend/image decoding/browser interaction, private reads after revocation, failed upload recovery, two-tab cleanup races and responsive/keyboard visual QA must pass against the configured dedicated backend before this feature is called production-validated. Check `STATUS.md` and the current test reports for actual results; these controls do not resolve infrastructure quotas or supply credentials.
